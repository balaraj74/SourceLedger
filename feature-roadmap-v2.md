# SourceLedger — Feature PRD & Roadmap (v2 / Post-MVP)

This extends `docs/prd.md` and `docs/architecture.md`. It does not replace them — Phases 0–6 in `prd.md`
remain the MVP baseline. This document defines **Phases 7–12**, each building on the existing agent pipeline
(`IngestionAgent → ExtractionAgent → EnrichmentAgent → ValidationAgent → ExplainabilityLayer`) rather than
introducing a parallel system. Phase 12 is an explicit stretch/optional bucket — do not let it dilute focus
on Phases 7–11, which remain the core deliverable.

**Non-negotiable constraint across every phase:** no field, dashboard number, graph edge, or UI value may ever
be a hardcoded constant, static default, or "reasonable placeholder." Every value must trace to (a) a real
extraction from a source, (b) a real computed aggregate over real records, or (c) an explicit `null` +
`needs_review` status. This directly closes the bugs found in production output — `UPC = 10000000000` and
`List Price = 24.99` repeated across every row, and `BRAND_NAME` generated by string-appending "®" to the
`Part_Manuf` distributor field instead of a real lookup. Each feature phase below includes an explicit
anti-hardcoding check as part of its Definition of Done.

**Visual constraint across every phase:** reuse the existing design system exactly — Tailwind v4 tokens
`#F5E9D8` (base), `#E8622C` (single accent), `#191715` (near-black text), the established muted
green/amber/red confidence coding, and the Field Inspector / Review Queue as the hero surfaces. No new
palette, no new component library, no gradients. New UI (dashboard, graph view, VLM diff viewer) must look
like it shipped with the existing app, not bolted on.

## Phase 7 — Cross-Source Conflict Resolution (extends `ValidationAgent`)

**Why:** `ValidationAgent` already does trust-tier ranking and confidence scoring per the architecture doc.
This phase makes conflicts *visible* instead of silently resolved, which is what "traceable outputs" in the
problem statement actually requires.

**Data model additions** (`backend/src/models/schemas.py`):
```python
class FieldConflict(BaseModel):
    field_name: str
    candidates: list[FieldCandidate]   # each: value, source_id, trust_tier, raw_excerpt
    resolution: str                    # which candidate value won
    resolution_reasoning: str          # why — e.g. "Tier 1 OEM source outranks Tier 3 catalog"
    resolved_confidence: int           # 0-100
```
- `FieldConflict` is only ever created when ≥2 sources disagree on the same field for the same record — never
  synthesized for single-source fields (that would itself be a fabrication).
- Store `FieldConflict` rows keyed to the existing `Field` entity; the Field Inspector reads them, it doesn't
  compute them at render time.

**Backend work:**
- Extend `ValidationAgent` to detect disagreement across sources *before* collapsing to a single value —
  currently it likely picks a winner directly; add an explicit diff step first.
- If sources agree, no `FieldConflict` row is created (avoid clutter — only surface real disagreement).
- If trust-tier ranking can't cleanly resolve (e.g. two Tier 1 sources disagree), force `needs_review` rather
  than picking arbitrarily.

**Frontend work (Field Inspector):**
- Add a "Sources disagree" indicator (reuse the existing amber confidence color, don't invent a new one) that
  expands to show each candidate value with its source excerpt side by side.
- This is additive to the existing Field Inspector layout — same card, same typography, new expandable section.

**Definition of Done:**
- [ ] A test batch with at least 2 deliberately conflicting sources produces a `FieldConflict` record, not a
  silently-picked value.
- [ ] Zero `FieldConflict` rows exist for fields with only one source (regression test).
- [ ] Field Inspector renders the conflict view using existing design tokens only.

## Phase 8 — Product Knowledge Graph (new component: `GraphAgent`)

**Why:** turns flat per-SKU records into linked product intelligence — directly answers "generate structured
product intelligence" beyond single-row enrichment, and gives you a real answer to duplicate/variant SKUs
already found in your own sample data (`DCB520ASTS08G` vs `DCB520ASTS08G-P120`; `AVM6EV` "Mini Snip Red" vs
"AVM7 EV Mini Snip Green" sharing one `Mfg_Part_Num`).

**Data model additions:**
```python
class ProductRelationship(BaseModel):
    source_sku: str
    target_sku: str
    relationship_type: Literal["variant_of", "substitute_for", "compatible_with", "accessory_for", "same_family"]
    confidence: int              # 0-100, same scale as Field confidence
    reasoning: str                # why the graph agent linked these
    evidence_field: str | None    # which shared attribute triggered the link (e.g. shared base part number, shared manufacturer + product line)
```

**Backend work — new `GraphAgent` (`backend/src/agents/graph_agent.py`):**
- Runs *after* `ValidationAgent`, operating on already-validated records (never links unvalidated/low-confidence
  data — a graph built on fabricated fields compounds the problem).
- Relationship detection must come from real signals already in the schema: shared `manufacturer` +
  overlapping `part_number` prefix/suffix pattern, shared `Classpath`, matching category-schema attributes
  (e.g. two `safety_fastener` records with identical `thread_size`/`material` but different `finish`).
- Every edge gets a `confidence` and `reasoning` — same explainability bar as any other field. No edge is
  created without both.
- Use the existing PostgreSQL/Supabase layer — a `product_relationships` table, not a separate graph database,
  to stay within the hackathon's stack and timeline (a proper graph DB is a good "if time permits," not a
  requirement).

**Frontend work:**
- A "Related Products" panel on the record view, visually consistent with the Field Inspector card style —
  same border radius, same spacing scale, accent color used only for the relationship-type badge.
- Clicking a related SKU navigates to that record's Field Inspector — this is the single most demoable moment
  for judges ("look, it caught that these are the same product family without being told").

**Definition of Done:**
- [ ] Graph edges only exist between records that have passed validation (no edges from `needs_review` records
  with unresolved conflicts).
- [ ] Every edge has non-null `confidence` and `reasoning` — enforced at the DB layer (NOT NULL constraint),
  not just convention.
- [ ] Demo dataset shows at least one correctly-detected variant family end to end.

## Phase 9 — Vision-Language Document Intelligence (extends `IngestionAgent` + `ExtractionAgent`)

**Why:** this is the "document intelligence / vision-language models" line item from the problem statement,
and it's also the legitimate way to fill fields your pipeline currently leaves blank or fabricates —
`UPC`, dimensions, `Country of Origin`, ratings — when the only real source is a spec-sheet table or a
nameplate photo, not clean text.

**Backend work:**
- Extend `IngestionAgent` to accept image/PDF-page inputs and route them to a VLM call (same Gemini
  multi-key rotation pool — `KeyRotator` already supports this, just add an image-capable request path).
- Extend the `Source` model with `extraction_method: Literal["text", "vlm_image", "vlm_pdf_table"]` so every
  field downstream can show *how* it was read, not just where from — this is an explainability upgrade, not
  just a new ingestion path.
- The VLM's read of an image is itself the "source excerpt" for citation purposes — store a cropped
  region/bounding-box reference alongside the raw extracted text where feasible, so the Field Inspector can
  show "this is the exact table cell/nameplate region the value came from."
- Confidence scoring for VLM-extracted fields should generally start more conservative than clean-text
  extraction (e.g. cap at a lower ceiling before human review) — OCR/VLM misreads are a known failure mode
  and the architecture doc already commits to "best-effort, flagged low-confidence when uncertain" for scans.

**Frontend work:**
- Field Inspector's source-excerpt view gains an image-region mode: show the source image with the relevant
  area highlighted, next to the extracted text. Same card chrome as the existing text-excerpt view — don't
  design a new component type for this, extend the existing one.

**Definition of Done:**
- [ ] At least one demo record's `UPC`/dimensions/etc. is genuinely sourced from an image/PDF table via VLM,
  with a real citation — not text-extracted, not hardcoded.
- [ ] `extraction_method` is visible in the Field Inspector for every field.
- [ ] A VLM extraction with low legibility (test with a deliberately blurry sample) degrades confidence and
  routes to `needs_review` rather than guessing — reuses the existing "graceful degradation" rule from
  `master-agent-prompt.md`.

## Phase 10 — Confidence-Based Active Learning (extends `ValidationAgent` + Review Queue)

**Why:** `ReviewAction` records already exist per the architecture doc — this phase makes the "improves with
use" narrative real and *demoable*, not just logged and forgotten.

**Data model additions:**
```python
class CorrectionPattern(BaseModel):
    category: str              # e.g. "industrial_pump"
    field_name: str
    manufacturer: str | None
    correction_count: int
    avg_confidence_before_correction: float
    last_updated: datetime
```
- Aggregated, computed from real `ReviewAction` history — never seeded with placeholder counts.

**Backend work:**
- After N corrections accumulate for the same `(category, field_name, manufacturer)` combination, adjust that
  combination's future confidence scoring in `ValidationAgent` — e.g. if reviewers consistently correct
  `flow_rate` extraction for a given manufacturer's pump datasheets, lower the auto-commit confidence for that
  specific pattern going forward until corrections stop, or raise it if the agent starts getting it right.
- This must be a real, computed adjustment (a small weighting factor derived from the `CorrectionPattern`
  table), not a cosmetic label — judges may ask to see the before/after numbers.

**Frontend work:**
- Add a small "Accuracy Trend" indicator to the Quality Dashboard (Phase 11) — e.g. a sparkline of
  auto-commit rate for a field/category over the session, computed live from real `ReviewAction` timestamps.

**Definition of Done:**
- [ ] A scripted demo sequence (correct the same field type 5–10 times) produces a visible, real change in
  that field's future confidence score or auto-commit rate — capture this as your strongest live demo moment.
- [ ] No trend/count is precomputed or faked for the demo — it must be reproducible live from a fresh batch.

## Phase 11 — Live Data Quality & Trust Dashboard (new: `backend/src/services/dashboard_service.py`)

**Why:** formalizes catalog-wide QA as a first-class feature, and doubles as the mechanism that would have
caught the fabrication bugs found in your own delivery files — this is not just a nice-to-have panel, it's
your regression safety net productized.

**Backend work — compute live, never cache stale/fake numbers:**
- Coverage: `% of input batch with a delivered record` (this must be a real query against the current run's
  input/output sets — Phase 7's addendum test #1, "output ⊆ current input," should be enforced here as a
  live-visible metric, not just a background assertion).
- Confidence distribution by category and field.
- `needs_review` count and aging (how long items have sat unreviewed).
- **Suspicious-fill detector**: for numeric/identifier fields (`UPC`, `List Price`, dimensions, etc.), flag
  any field where a single value repeats across more than a small threshold (e.g. 5%) of *distinct* products
  in the current batch. This directly productizes the exact check that would have caught the
  `UPC = 10000000000` / `List Price = 24.99` bug — surface it as a red-flag panel a Catalog Manager would
  actually use, not just a CI assertion.
- Classification diversity check: flag if one `Dept/Class/Fine` path covers a disproportionate share of a
  batch relative to how varied the underlying descriptions are (closes the "everything defaults to General"
  bug).

**Frontend work:**
- One dashboard screen, data-dense but calm per the existing UI direction in `master-agent-prompt.md` —
  numbers and small charts, muted confidence-tier colors, `#E8622C` used only for primary actions/alerts, not
  decoration.
- Suspicious-fill and classification-diversity flags render as an actionable list (click through to the
  affected records in the Review Queue), not just a static warning.

**Definition of Done:**
- [ ] Every number on the dashboard is a live query result, not a constant — verified by running it against
  two different-sized batches and confirming the numbers actually change.
- [ ] The suspicious-fill detector fires correctly against a deliberately-seeded test batch with a repeated
  fake UPC, and does *not* fire on a clean batch with legitimately varied values.

## Cross-Phase: Anti-Hardcoding Enforcement (add once, applies to all of Phases 7–11)

Add an automated check, run as part of the existing test suite / CI, before any phase is marked done:

```python
def test_no_fabricated_constants(batch_output):
    """Fails if any numeric/identifier field shows implausible uniformity across distinct products."""
    for field in ["UPC", "EAN", "GTIN", "List Price", "Warranty", "LENGTH", "WEIGHT"]:
        values = batch_output[field].dropna()
        if len(values) > 5:
            most_common_share = values.value_counts(normalize=True).iloc[0]
            assert most_common_share < 0.05, f"{field} is suspiciously uniform ({most_common_share:.0%} identical)"
```

Wire this into whatever runs after `run_batch_processing.py` completes a batch — treat a failure as a build
blocker, exactly as `master-agent-prompt.md` already treats a missing citation as a bug, not a cosmetic gap.

## Phase 12 — Stretch / Optional (only after Phases 7–11 are solid)

These are real, useful features — but explicitly lower priority than the core roadmap. Do not start any of
these until every Phase 7–11 Definition of Done is met and verified. Pick based on time remaining; each is
independent of the others, so partial completion is fine.

### 12a. Batch progress + concurrency visibility (quick win)
- Expose a live progress view during a batch run: X/N processed, current concurrency, ETA, using the
  per-item timing already logged per `master-agent-prompt.md`'s "log every agent step's input/output/duration"
  rule — this is wiring, not new instrumentation.
- Render as a simple progress bar/counter on the existing dashboard shell (Phase 11), same design tokens.
- **Anti-hardcoding check:** ETA must be computed from real observed per-item timing in the current run, not
  a static assumed rate.

### 12b. One-click bulk correction (quick win)
- When a reviewer corrects a field for one record (e.g. a `Part_Manuf` → `MANUFACTURER_NAME` mapping), offer
  to apply the same correction to every other `needs_review` record sharing the same source value pattern in
  the current batch, in one action.
- Builds directly on the existing `ReviewAction` log — add a "matching records" query before writing the
  bulk `ReviewAction` entries (one per affected record, not a single record standing in for many — keep the
  audit trail honest).

### 12c. Multi-format export (quick win)
- Add a JSON export (schema.org/Product-shaped) alongside the existing CSV delivery format, generated from
  the same validated `ProductRecord` — no new extraction, just an additional `CSVProcessor`-sibling exporter.
- Demonstrates "commerce-ready ... for any commerce system" from the problem statement with near-zero
  incremental extraction risk.

### 12d. Compliance/certification completeness check (medium effort)
- Your schema already carries `Standard/Approvals`, `RoHS`, `Prop 65`, `SDS`. Add a per-category rule (e.g.
  `safety_fastener` missing `certifications`, or `power_tool` missing `RoHS`) that routes to a distinct
  "compliance review" queue, separate from generic low-confidence review.
- This is domain-specific to industrial commerce — a strong differentiator versus a generic PIM demo — and
  reuses fields that already exist in the schema, so no new ingestion work is required.

### 12e. Catalog Q&A over structured records (medium effort)
- A thin retrieval layer over already-validated `ProductRecord`s (not new source extraction) answering
  natural-language questions like "which pumps have flow rate over 40 m³/h and are auto-committed."
- Explicitly checks the "RAG" line item in the problem statement as a capability distinct from the
  extraction-time RAG you already do — frame it that way in the pitch, since judges may otherwise assume it's
  the same thing.
- **Anti-hardcoding check:** answers must be generated by querying real record data at request time — no
  precomputed/cached answer set for specific demo questions.

### 12f. Empirical source trust scoring (medium effort, depends on Phase 10)
- Evolve the static Tier 1/2/3 trust ranking in `ValidationAgent` into a score that adjusts based on how
  often a given source domain's values get corrected in the Review Queue over time — the same active-learning
  mechanism as Phase 10, applied to sources instead of field/category patterns.
- Only start this once Phase 10 is working and you have real correction volume to learn from — an empirical
  trust score with no data behind it is itself a fabricated value.

### 12g. Lower priority — do only if everything else is done
- Field-level version history across re-ingestions (auditability nice-to-have, unlikely to be judged live).
- A PDF "trust report" export per record/batch (better suited to the pitch deck than the live demo).
- Cost/token-usage dashboard for the Gemini key pool (operationally useful, not something judges score).

## Suggested Build Order

1. Phase 7 (Conflict Resolution) — smallest, extends existing `ValidationAgent` directly, high explainability payoff.
2. Phase 11 (Dashboard) — cheap relative to its payoff, and gives you the anti-hardcoding safety net before
   building more features on top of a pipeline you now know has fabrication bugs.
3. Phase 8 (Knowledge Graph) — highest demo "wow" factor, moderate effort given the schema/relational layer
   already exists.
4. Phase 9 (VLM Document Intelligence) — checks the explicit problem-statement box, but is the most
   integration-heavy; timebox it and fall back gracefully (per the existing Phase 6 fallback framing) if it's
   not stable by demo day.
5. Phase 10 (Active Learning) — do last; it depends on having real `ReviewAction` volume from the earlier
   phases being used first.
6. Phase 12 (Stretch) — only after 7–11 are done and verified. Within Phase 12, do the quick wins (12a–12c)
   before the medium-effort items (12d–12f), and treat 12g as filler only if there's genuinely nothing left
   to harden.
